# TLS 1.3 в pagh-riscv

Клиент TLS 1.3 в ядре: `https://` ходит **свой** TCP-клиент (`src/net/tcp.rs`),
рукопожатие ведёт vendored `embedded-tls` 0.19.0, а решение «доверять ли
серверу» принимает не крейт, а собственный проверяющий слой ядра. Ни один
байт приложения не уходит раньше, чем цепочка сертификатов сойдётся с
закоммиченным CA-бандлом, SAN авторизует имя, часы пройдут clock gate, а
`CertificateVerify` проверится ключом листа.

Это порт x86-соседа ([Pagh-OS](https://github.com/ccclosed/Pagh-OS),
`src/net/tls.rs` + `vendor/embedded-tls`). Отличия и честные пробелы —
в конце документа.

## Что где лежит

| Файл | Роль |
|---|---|
| `src/net/tls.rs` | ядро порта: `KernelRng`, `KernelVerifier`, `KernelProvider`, транспорт поверх `tcp.rs`, `block_on`, `https_get`/`https_get_at` |
| `src/net/ca_bundle.rs` | **сгенерированный** trust-anchor бандл: 6 самоподписанных корней, DER + метка CN |
| `tools/gen_ca_bundle.py` | генератор бандла: скачивает `https://curl.se/ca/cacert.pem`, выбирает корни **по sha256-пину**, сверяет CN из DER, требует самоподписанности, форматирует `rustfmt`. Пайплайн `generate + rustfmt` детерминирован |
| `src/net/x509.rs` | минимальный DER-ридер и разбор X.509 (чистый `core`, без паник) |
| `src/net/tls_chain.rs` | сборка пути лист → промежуточные → якорь, подписи, `cA=TRUE`, окна валидности, clock gate |
| `src/net/tls_auth.rs` | одно решение «пускать ли этот сервер»: цепочка + SAN + экспорт ключа листа + `CertificateVerify` |
| `src/net/tls_verify.rs` | бэкенды проверки подписей: RSA PKCS#1 v1.5 (SHA-256/384/512), ECDSA P-256/P-384, Ed25519 |
| `src/net/hostname.rs` | RFC 6125: `dNSName` и `iPAddress`, без CN-fallback |
| `src/net/http.rs` | чистые `build_get_request` / `parse_http_head` + инкрементальный декодер `Transfer-Encoding: chunked` |
| `src/drivers/rtc.rs` | goldfish RTC (часы): наносекунды от эпохи, латч низкого слова |
| `src/entropy.rs` | пул энтропии: `/chosen/rng-seed` + jitter, SHA-256 ratchet, fail-closed |
| `tools/test_tls.py` | живая приёмка (5 проверок) → `docs/live-tls.txt` |

## Порядок одного `https_get`

1. **Preflight (fail-closed, до сокета).** Нет seed'а в пуле энтропии →
   `NoEntropy`; нет RTC → `NoClock`; нет DHCP-lease → `NoNetwork`.
2. **Резолв** имени (`dns::resolve`) — или адрес, пришпиленный вызывающим
   (`https_get_at`, shell-форма `--ip`).
3. **TCP**: `tcp::connect` (свой стек, три рукопожатия, ограниченный дедлайн).
4. **`embedded-tls` ClientHello** с `server_name` = хост (SNI) и единственным
   шифр-сьютом `TLS_AES_128_GCM_SHA256`.
5. **Проверка сертификата** (см. ниже) — на этом шаге `embedded-tls` вызывает
   `KernelVerifier::verify_certificate`.
6. **`CertificateVerify`** — подпись по RFC 8446 §4.4.3 (64 пробела + контекст
   + хеш транскрипта) проверяется ключом **того же** листа.
7. **Belt-and-braces**: `https_get` снимает счётчик `VERIFIED_HANDSHAKES` до
   рукопожатия и отказывается слать запрос, если после `open()` счётчик не
   вырос. Vendored `embedded-tls` патчен так, чтобы `Finished` без
   `Certificate`/`CertificateVerify` отклонялся; счётчик — вторая,
   независимая проверка того же факта.
8. **HTTP/1.1 GET** и разбор ответа: `Content-Length` **или**
   `Transfer-Encoding: chunked` (Cloudflare на `example.com` отвечает именно
   chunked, без `Content-Length`). Конец тела — только явный (нулевой чанк или
   полный Content-Length); обрыв потока телом не считается.

## Что именно проверяется у сертификата

Порядок и жёсткость зафиксированы в `tls_auth::authenticate_server`:

1. **Цепочка** (`tls_chain::verify_chain`):
   * каждое звено подписано ключом издателя (RSA PKCS#1 v1.5 / ECDSA P-256 /
     P-384 / Ed25519) — по OID из `tbsCertificate.signature`;
   * у каждого издателя (промежуточного и корня) `basicConstraints cA=TRUE`;
     **отсутствие** расширения — отказ (DER опускает default FALSE);
   * `notBefore ≤ now ≤ notAfter` **у всех** сертификатов сообщения;
   * `now ≥ CLOCK_FLOOR` (2025-01-01T00:00:00Z) — часы ниже порога означают
     «время неизвестно», а не «всё валидно»;
   * путь заканчивается **якорем из `ca_bundle`**, а не сертификатом из
     сообщения. Якоря пробуются **первыми** — см. «Находка порта» ниже.
   * RSA-PSS в X.509 отклоняется явно (параметры PSS живут в сертификате,
     который контролирует peer); `rsa_pss_*` в `CertificateVerify` — наоборот,
     обязательный и поддерживаемый случай TLS 1.3.
2. **SAN** (`hostname.rs`): цель авторизуется **только** записями
   `subjectAltName` листа — `dNSName` для имени, `iPAddress` для литерала;
   CN не рассматривается; отсутствие/порча SAN — отказ.
3. **Ключ листа** экспортируется в `LeafKey`; неподдерживаемый алгоритм —
   отказ на этом шаге, а не «потом».
4. **`CertificateVerify`** — подпись проверяется ключом экспортированного
   листа; ширина хеша транскрипта берётся из **шифр-сьюта** (32 для
   SHA-256), схема подписи выбирает только дайджест (SHA-384/512-схемы
   проверяемы над 32-байтовым транскриптом — это не ошибка).

Любой отказ печатает одну строку `tls: verify FAILED cause=…`
(`chain` / `hostname` / `clock` / `no-hostname` / `leaf-key` /
`signature-scheme` / `signature`), а shell-сводка называет шлюз:
`https: FAILED: certificate rejected (chain)`.

## Trust anchors: что и почему закоммичено

`ca_bundle.rs` — **сгенерированный** файл; руками не правится. `SELECTION` в
`tools/gen_ca_bundle.py` пинует каждый корень по sha256 и сверяет CN из DER,
поэтому подмена корня в источнике не проходит молча. Сейчас в бандле 6
якорей:

| Якорь | Зачем |
|---|---|
| ISRG Root X1, X2 | Let's Encrypt-поверхность (apt-зеркала, половина интернета) |
| GTS Root R1, R4 | Google Trust Services (CDN-края) |
| SSL.com TLS ECC Root CA 2022 | **добавлен портом**: `example.com` (Cloudflare) цепится сюда |
| SSL.com TLS RSA Root CA 2022 | вторая половина issuance SSL.com + RSA-путь проверки |

Расширение бандла — это осознанный акт: добавить пару `(CN, sha256)` в
`SELECTION`, перегенерировать, закоммитить. Больше якорей = шире доверие,
поэтому список остаётся коротким и объяснимым.

## Находка порта: cross-signed корень и порядок обхода

Cloudflare отдаёт для `example.com` **четыре** сертификата, и последний —
cross-signed копия корня `SSL.com TLS ECC Root CA 2022`, подписанная чужим CA
(`AAA Certificate Services`). Жадный обход «сначала сертификаты из сообщения»
уходил в эту копию и упирался в незнакомого издателя: `ChainError::NoAnchor`
на полностью валидной цепочке.

Исправление: **якоря пробуются раньше сертификатов сообщения**. Это не
расширяет доверие — принять по-прежнему можно только при совпадении `Name`
байт-в-байт с якорем **и** проверенной подписи его ключом. Меняется лишь
порядок поиска. Остаточное ограничение (успешный шаг в кандидата, который
дальше никуда не ведёт, не откатывается) может только **отклонить** лишнее,
никогда — принять лишнее.

Проверено офлайн на настоящей цепочке `example.com` (host-стенд, те же самые
файлы `src/net/*.rs`): полная цепочка — OK; без cross-signed корня — OK;
подмена байта в листе — `Verify(VerifyFailed)`; чужой хост —
`HostnameMismatch`; часы ниже порога — `Clock`; чужой набор якорей —
`NoAnchor`.

## Часы

Валидность сертификата нельзя проверить без времени, а RISC-V `virt` не имеет
CMOS. Часы берутся из **goldfish RTC** (`compatible = "google,goldfish-rtc"`,
`rtc@101000` в дереве устройств): 64-битный счётчик наносекунд от эпохи,
чтение `TIME_LOW` защёлкивает `TIME_HIGH`. Окно регистров приходит из FDT (не
из константы) и маппится как device memory вместе с UART/PLIC/virtio. Строка
загрузки печатает и дату, и сырые регистры — неверные часы видны до любого
рукопожатия. Нет узла RTC → `now_unix()` = `None` → отказ `cause=clock`.

## Энтропия

Сессионные ключи нельзя брать из счётчиков. Источник — **`/chosen/rng-seed`**:
QEMU (как и для Linux) кладёт в FDT 32 байта хостовой случайности. Они
впитываются в пул вместе с 32 пробами jitter'а (RTC, `time` CSR, тики,
адрес стека) через SHA-256; генератор — SHA-256 ratchet
(`block = H(state ‖ counter)`, затем `state = H(state ‖ 0x01 ‖ block)`), что
даёт обычную backtracking-resistance. `entropy::is_available()` = false, пока
seed не впитан, и `https_get` в этом случае **отказывает до открытия сокета**.

Честно: это **не** аппаратный CSPRNG. 256 бит хостового seed'а — сильный
корень, jitter — defence in depth, а не учтённая энтропия. На машине без
`/chosen/rng-seed` TLS не работает вовсе (та же политика, что «нет RDSEED — нет
TLS» на x86), а не деградирует до предсказуемых ключей.

## Транспорт и его пределы

`TlsTransport` реализует `embedded_io_async::Read/Write` поверх **единственного**
active-open TCP-соединения своего стека. Чтение — неблокирующие сливы по
`recv_nonblocking_id` до опустошения сокета; запись — `send_id`, ждущий ACK
(поэтому `flush` — no-op). Inactivity-бюджет 20 с перевзводится на каждом
байте; `block_on` между poll'ами уходит в `wfi` на тик, а не крутится.

Пределы, которые стоит знать: у TCP 4 KiB приёма и окна, нет ретрансмиссионных
таймеров и out-of-order reassembly (это QEMU-локальная модель), поэтому
рукопожатие и тело едут короткими окнами — медленно, но корректно, пока peer
уважает окно. Один `https` за раз: это один сокет.

## Как это проверить

```sh
cargo build --locked
python3 tools/test_tls.py          # нужен интернет у хоста и QEMU
```

`tools/test_tls.py` делает пять вещей в одном прогоне и требует ровно тех
исходов, которые заявляет:

1. `entropy` — пул засеян (32 байта из `/chosen/rng-seed`);
2. `https https://example.com/` — настоящее рукопожатие, проверенная цепочка,
   SAN, тело `Example Domain` (в транскрипте: `tls: verified leaf=sha256:…`,
   `CertificateVerify OK`, `handshake OK`, `fetch OK body=…`);
3. **негатив по цепочке**: локальный `openssl s_server` с самоподписанным
   сертификатом **на правильное имя** `example.com` — сокет доступен, имя
   верное, сертификат недоверенный → `cause=chain`;
4. **негатив по SAN**: реальный сервер, чья цепочка **сходится** к пину
   (`GTS Root R1`/`R4`), но чей сертификат не покрывает `example.com` →
   `cause=hostname` (скрипт проверяет эту предпосылку с хоста, чтобы вердикт
   не оказался верным по случайности);
5. **негатив по резолву**: `no-such-host.invalid` падает на `stage=resolve`,
   не открывая сокет.

Полный транскрипт — `docs/live-tls.txt`.

## Чего нет (честно)

- **Отзыва (CRL/OCSP) нет**, CT-логов нет, pinning'а сверх бандла нет.
- **Бандл — это 6 пинов, а не «весь Mozilla store».** Хост, чья цепочка
  укоренена в другом корне (DigiCert, Sectigo, …) или в корне новее
  зафиксированных, получает `cause=chain`. На момент написания (2026-11-09) в
  пинах нет, например, `ISRG Root YR`: Let's Encrypt уже выдаёт через него
  (`YR1`), а используемый генератором extract `curl.se/ca/cacert.pem` его ещё
  не содержит. Лечится расширением `SELECTION` — но это осознанный пересмотр
  доверия, а не «обновление зависимости».
- **Нет session resumption / 0-RTT / PSK, клиентских сертификатов, ALPN,
  TLS 1.2 и ниже.** Только TLS 1.3, только `TLS_AES_128_GCM_SHA256`.
- **Нет переиспользования соединений** (keep-alive): один `https` — один
  сокет — один обмен.
- **RNG не аппаратный** (см. выше): 32 байта хостового seed'а на загрузку,
  растянутые SHA-256 ratchet'ом.
- **`pkg`/apt по-прежнему plain HTTP** и без OpenPGP: TLS добавлен как
  транспортный слой и shell-путь, установщик пакетов на него не переведён.
- **Медленно.** Проверка RSA/P-384 и AES-GCM без ускорения под TCG — секунды
  на рукопожатие; TCP с 4 KiB окном добавляет RTT'ы.
- **Переиспользование кода x86-модулей без host-property-тестов**: в этом
  репозитории нет `host-tests`, поэтому чистые `x509`/`tls_chain`/`tls_auth`/
  `tls_verify` проверены офлайн-стендом (см. выше) и живой приёмкой, а не
  свойствами в CI.
