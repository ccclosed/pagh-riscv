# Руководство для контрибьюторов pagh-riscv

Спасибо, что хотите поучаствовать в `pagh-riscv` — небольшом 64-битном ядре для
RISC-V (RV64) на Rust (`#![no_std]`, без внешних зависимостей, загрузка через
OpenSBI, запуск в QEMU). Это хобби-/учебный проект: здесь ценятся честная
документация, аккуратные коммиты и сохранение инвариантов загрузки.

---

## 1. С чего начать

1. Прочитайте [`README.md`](README.md) целиком — там статус каждой подсистемы
   («что работает сегодня» и «чего нет»).
2. Прочитайте [`docs/architecture.md`](docs/architecture.md) — порядок фаз
   загрузки, формат кадра ловушки, модель привилегий, карта памяти. Это то, что
   нельзя менять, не заметив.
3. Просмотрите [`docs/roadmap.md`](docs/roadmap.md) — что задумано дальше и что
   сознательно вне области.
4. Если трогаете экран или снимаете скриншоты — [`docs/screenshot.md`](docs/screenshot.md):
   как устроен `tools/run.py` и что именно доказывает `font_check.py`.
5. Если вы ИИ-агент (или работаете с ним) — [`AGENTS.md`](AGENTS.md) содержит те же
   правила в виде списка инвариантов и команд.

Для крупных изменений сначала опишите подход в issue: дешевле обсудить фазу
загрузки, чем переделывать её.

## 2. Окружение

| Что | Зачем |
|---|---|
| Rust nightly из `rust-toolchain.toml` (`nightly-2026-07-12`) | ядро собирается только им; версия запинена, не обновляйте её мимоходом |
| `rustup target add riscv64gc-unknown-none-elf` | целевая платформа (`.cargo/config.toml`) |
| `qemu-system-riscv64` | запуск и smoke-тест; на Fedora/Debian это пакет `qemu-system-misc` |
| Python 3 | `.github/smoke.py` (только стандартная библиотека) |

Windows-путь не поддерживается: `run.cmd`/PowerShell-харнессы из x86-репозитория
сюда не портированы, и добавлять их «для паритета» не нужно.

## 3. Сборка и запуск

```sh
cargo build            # debug-ядро: target/riscv64gc-unknown-none-elf/debug/pagh
cargo build --release  # release (opt-level = "s", lto)
./run.sh               # QEMU virt + OpenSBI, серийная консоль
```

Выход из QEMU — `Ctrl-A`, затем `X`. Изнутри гостя — команда `halt`: она
выключает машину через SBI SRST, и QEMU завершается сам.

| Переменная `run.sh` | По умолчанию | Смысл |
|---|---|---|
| `PROFILE` | `debug` | `PROFILE=release` — собрать и запустить release |
| `MEMORY` | `256M` | размер RAM у машины `virt` |
| `BIOS` | QEMU `-bios default` | внешний файл прошивки OpenSBI |

Экран включён по умолчанию: `run.sh` передаёт `-device ramfb` и `-display none`,
то есть рисует поверхность off-screen (её можно снять без графической сессии).
`./run.sh --window` открывает то же самое окном QEMU (нужен дисплей), `--headless`
— явная форма поведения по умолчанию; неизвестный аргумент — ошибка, а не тихий
игнор. Чтобы увидеть экран без `run.sh` (или снять его скриптом):

```sh
qemu-system-riscv64 -machine virt -m 256M -device ramfb \
  -kernel target/riscv64gc-unknown-none-elf/debug/pagh -display none -serial stdio

python3 tools/run.py --keys "help\n" --shot /tmp/shot.png --check-font --scan-all
```

Как это работает и что проверяет `font_check.py` — см.
[`docs/screenshot.md`](docs/screenshot.md).

Строку запуска без `run.sh` можно собрать руками:

```sh
qemu-system-riscv64 -machine virt -m 256M \
  -kernel target/riscv64gc-unknown-none-elf/debug/pagh \
  -nographic -no-reboot
```

## 4. Проверка: гейты CI

Перед PR должны быть зелёными все перечисленные команды; CI запускает ровно их
(`.github/workflows/ci.yml`): `fmt` и обе сборки — отдельными job'ами, два режима
smoke — двумя шагами одного job'а.

```sh
cargo fmt --all -- --check                                              # формат
cargo build --locked                                                    # debug
cargo build --locked --release                                          # release
python3 .github/smoke.py target/riscv64gc-unknown-none-elf/debug/pagh           # serial
python3 .github/smoke.py target/riscv64gc-unknown-none-elf/debug/pagh --ramfb   # + экран
```

Что проверяет smoke: ядро поднимается, печатает баннер, строки DTB и строку пула
кадров, отвечает на `mem`, `hart`, `time`, `echo`, неизвестную команду и `help`,
а после `halt` машина действительно выключается (QEMU exit code 0). Режим
`--ramfb` дополнительно требует строку `framebuffer  ramfb …`, то есть проверяет
и путь экрана. Команды отправляются **после** появления баннера: `uart::init`
очищает FIFO, и всё, что пришло раньше, теряется.

Две проверки, которые запускаются вручную (в CI пока не входят):

```sh
# в госте, на приглашении pagh:rv64>
selftest                    # четыре проверки памяти: SELFTEST … PASS/FAIL + ledger кадров
# на хосте
python3 tools/run.py --keys "help\n" --shot /tmp/shot.png --check-font --scan-all
```

`selftest` — образец для подсистем, владеющих состоянием: проверки
неразрушающие и идемпотентные, а в конце печатается ledger свободных кадров
(`[selftest] PMM hygiene: free frames X -> Y`). Если routine что-то не вернул
на место, два прогона в одной загрузке разойдутся — это и есть детектор утечки.
Host-тестов в дереве пока нет вовсе; для чистой логики (например `fdt.rs`)
шаблон можно взять из x86-репозитория.

Правило: *исправление регрессии без проверки не считается сделанным*. Минимальный
шаг — ожидаемая строка в `EXPECTED` внутри `.github/smoke.py`; для состояния —
`SELFTEST`-routine; для пикселей — `--check-font`.

## 5. Как добавить подсистему

1. **Папка и модуль.** `src/<имя>/mod.rs` + файлы; объявите модуль в `src/main.rs`
   (или в родительском `mod.rs`). Порядок объявлений не важен, порядок **фаз** —
   важен.
2. **README рядом с кодом.** `src/<имя>/README.md`: что подсистема владеет, какие
   инварианты, что не реализовано. README живёт в том же коммите, что и код.
3. **Фаза загрузки.** Если подсистема инициализируется при старте — встройте её в
   `kmain` (`src/main.rs`) в правильное место и объясните комментарием, почему
   именно туда. Обновите таблицу фаз в `docs/architecture.md` (раздел 3) и карту
   памяти (раздел 6), если добавились символы или диапазоны.
4. **Проверяемость.** Если подсистема видна снаружи (команда шелла, строка лога) —
   добавьте её маркеры в `.github/smoke.py`. Если она владеет состоянием — добавьте
   `SELFTEST <имя> PASS/FAIL` рядом с `memory/selftest.rs` и печатайте ledger того
   состояния, которое обязаны вернуть на место: два прогона в одной загрузке
   должны сойтись. Для чистой логики — host property-тест (шаблон в x86-репозитории).
   Без этого проверить подсистему будет нечем.
5. **Документация статуса.** Обновите таблицу «Что работает сегодня» в
   `README.md` и статус майлстоуна в `docs/roadmap.md`.
6. **Гейты.** `cargo fmt --all`, `cargo build --locked` (debug и release), smoke.
7. **Коммит.** `area: императивное описание` — например `drivers: add virtio-mmio
   block device`. В теле — почему и что сломается без этого.

Если меняете поведение существующей подсистемы, шаги 2 и 5 обязательны: README
подсистемы и корневой статус — часть контракта.

## 6. Правила дома

* **Комментарии несут дизайн.** Doc-комментарии объясняют контракты («почему так»,
  «что сломается иначе»), а не пересказывают код. Плотность — как у соседних
  файлов; меняете поведение — меняйте комментарий в том же коммите.
* **Каждый `unsafe` — с `SAFETY:`.** Блок, asm-вставка, `static mut` — всё, без
  исключений. Автоматического гейта пока нет (в x86 есть `tools/check_safety.py`),
  поэтому это дисциплина, а не проверка.
* **Каждая подсистема документирует себя.** `src/<подсистема>/README.md` — не
  украшение: он должен совпадать с кодом. Устаревшая документация здесь
  считается багом.
* **Один hart, никаких «потоков».** Ядро работает на hart 0; остальные
  запаркованы в `_start`. Не добавляйте конкурентность, не описав её модель.
* **Никаких зависимостей.** `Cargo.toml` пуст по замыслу: крейты не подключаются.
  `alloc` при этом доступен — есть `#[global_allocator]` и куча на 64 KiB-чанках
  (`src/memory/heap.rs`), — но на boot-пути никто не аллоцирует, а драйверы
  намеренно живут на фиксированных статиках: драйвер, который не может работать до
  готовности пула кадров, не должен зависеть от кучи. Добавление внешнего крейта —
  архитектурное решение, а не деталь реализации; обсуждайте его отдельно.
* **M-mode — не наш.** `mhartid` и прочие M-mode CSR из S-mode недоступны;
  единственная дверь — `ecall` (SBI). Проверено на практике: чтение `mhartid`
  убивает машину (`illegal instruction`, `scause = 2`).
* **Не угадывать машину.** Всё, что можно прочитать из device tree, читается из
  него; ошибка разбора — фатальна и громкая. Единственная константа — адрес UART,
  и только потому, что консоль нужна раньше дерева.
* **Не трогайте чужие файлы.** Параллельные потоки работы (код / документация)
  владеют своими путями; правка «заодно» ломает чужой diff.
* **Не коммитьте артефакты.** `target/`, `*.log`, `*.img`, локальные прошивки — в
  `.gitignore`. Скриншоты коммитятся только снятые с работающего ядра.
* **Версия — в двух файлах.** `Cargo.toml` и `Cargo.lock` двигаются одним
  коммитом: CI собирает с `--locked` и падает иначе. Правила MAJOR/MINOR/PATCH —
  в `AGENTS.md`, раздел Versioning.

## 7. Стиль

Rust 2021, `#![no_std]`, `#![no_main]`. Комментарии и документация — по-русски,
идентификаторы, команды и имена файлов — по-английски. Таблицы и короткие
предложения предпочтительнее абзацев: документацию читают, чтобы проверить факт.
Строки, которые проверяет smoke-тест, менять можно только вместе с
`.github/smoke.py`.

## 8. Чем заняться

Ближайшее — [`docs/roadmap.md`](docs/roadmap.md): M2 (память) и M4 (framebuffer)
уже в работе, M3/M5/M6 ждут. Полезные задачи «на разогрев», все проверяемые:

| Задача | Почему полезна |
|---|---|
| Sv39 (M2b): таблицы страниц, `satp`, трансляция DMA-адресов | последняя часть M2; предупреждение о DMA уже стоит в шапке `src/drivers/fw_cfg.rs` |
| Убрать предупреждения сборки | мёртвые CSR-хелперы скрывают настоящие; предупреждений не должно быть «нормой» |
| Добавить `LICENSE` | `Cargo.toml` объявляет MIT, файла нет |
| Построить host-тесты для `fdt.rs` | чистая логика разбора — идеальный кандидат; шаблон есть в x86 |
| Добавить `--check-font` в CI | проверка пикселей уже возвращает код возврата и работает headless — готовый гейт для M4 |

## 9. Если нашли проблему

Приложите серийный лог целиком (QEMU + OpenSBI + строки ядра), версию QEMU
(`qemu-system-riscv64 --version`), версию тулчейна (`rustc --version`) и ревизию
дерева (`git rev-parse --short HEAD`). Для сбоя ядра особенно ценны строки
`[EXC] …`: там есть `scause`, `stval`, `sepc` и `ra`, по которым видно, где
именно всё сломалось. Без лога разбор начинается с «а как воспроизвести».
